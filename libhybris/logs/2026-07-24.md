## Storage architecture investigation

Idea: drop separate ext4 partitions entirely. One big `userdata`
partition, formatted Btrfs after install, with subvolumes instead of
partitions:

```
userdata (btrfs)
├── @android_data
├── @steamos_root
├── @steamos_home
├── @cache
├── @snapshots
└── @images
```

The installer wouldn't run `mkfs.ext4`, it would run
`mkfs.btrfs /dev/block/by-name/userdata` and then
`btrfs subvolume create @android` / `@steamos` / `@home` etc. - Android
keeps using `/data` (backed by a subvolume), Linux mounts its own
subvolume. This gets snapshots/rollback (matches PHASE 10's "Immutable
root, A/B updates, Rollback, Snapshots, Atomic updates") essentially for
free across the whole storage layout, not just the OS side.

**Real blocker found the same day, checked directly against actual
hardware data, not assumed**: Android almost never ships kernels with
Btrfs support (ext4/F2FS are the near-universal defaults), and this
matters here specifically because Android (as a Halium guest, see
`libhybris/SCOPING.md`) and the CR(g) OS host **share one kernel** -
there's no separate Android kernel to have its own filesystem support,
unlike a real dual-boot device. Checked the actual RP6 kernel extracted
from LineageOS (`libhybris/src/rp6-lineageos-prebuilt/out-boot/kernel`):
pulled its embedded IKCONFIG directly out of the binary (found the
`IKCFG_ST`/`IKCFG_ED` markers, extracted and gunzipped the embedded
`.config` - a real technique, not guesswork) -

```
# CONFIG_BTRFS_FS is not set
CONFIG_EXT4_FS=y
CONFIG_F2FS_FS=y
```

Also checked all 241 real vendor `.ko` modules and `vendor_dlkm.img` for
a loadable `btrfs.ko` - not present either way. **Btrfs is genuinely
absent from this kernel, confirmed, not assumed.**

Two real paths forward:
1. Enable Btrfs in the kernel. Either the full from-source rebuild (the
   Bazel/Kleaf path already paused once for being an open-ended risk -
   see SCOPING.md), or - untried, worth checking first - build just
   `btrfs.ko` as an out-of-tree module against this exact kernel's
   vermagic (`5.15.208-g94a246947232`), which is much lighter if the
   matching `Module.symvers`/headers are obtainable without the full
   Kleaf workspace.
2. Don't put Android's own `/data` on Btrfs at all - keep it ext4 (as
   shipped), and give only the CR(g) OS side the unified Btrfs/subvolume
   treatment on a separate area.

**Path 1 checked directly - it's a dead end, not a shortcut.** Tried
building `btrfs.ko` as an out-of-tree module against `kernel/ayn/qcs8550`
(Linux 5.15.208, matches the shipped kernel exactly) using the real
extracted `.config`. The kernel is built with `CONFIG_CFI_CLANG=y` +
`CONFIG_LTO_CLANG_FULL=y` + `CONFIG_MODVERSIONS=y` - Control Flow
Integrity and full Link-Time-Optimization are Clang-only hardening
features that fundamentally change function-pointer call-site ABI; a
module built with a different compiler (tried this host's GCC) would not
load into a CFI+LTO kernel at all, and `MODVERSIONS` additionally
requires matching per-symbol CRCs from the *exact* original build's
`Module.symvers`, which only exists as a build artifact we don't have.
Getting a loadable module therefore needs the same near-exact toolchain
match (Android's own `clang-r563880c`) and enough of a real rebuild to
regenerate a matching `Module.symvers` - i.e. this "lighter" path
converges back onto the same from-source Bazel/Kleaf work already paused,
not a shortcut around it. **Decision recorded as ADR-004: path 2.**

## First real RP6 boot image assembled

Built the first actual flashable boot-image test, not just planning.
Key realization while unpacking the stock firmware more carefully: since
`boot.img`'s ramdisk is empty (kernel-only, confirmed via
`unpack_bootimg.py`), the *real* first-stage init lives in
`init_boot.img` - a genuine, statically-linked AOSP `init` binary
(confirmed via `file`). Decided against reimplementing Android's own
init protocol from scratch (AVB chain, `androidboot.*` cmdline parsing,
etc.) - too much surface to get right blind. Instead: **keep boot.img/
vendor_boot.img/dtbo.img completely unchanged** (byte-identical to the
real stock firmware, already proven bootable on this exact hardware),
and replace only `init_boot.img`'s ramdisk with a minimal custom one.

Real consequence found while building this, not before: since PHASE 1
now commits to the real stock kernel (ADR-007), and that kernel has no
Btrfs support (confirmed via IKCONFIG, same as the LineageOS kernel),
the *entire* system - not just Android's own `/data` - has no Btrfs
available without the already-rejected from-source kernel rebuild
(logged as a consequence of ADR-007, `DECISIONS.md`). Used plain ext4
for the Arch rootfs image instead - not a workaround, a real
architecture correction, documented as such.

**Storage placement, per explicit user direction ("one system, shared
access")**: the Arch rootfs lives as a plain file
(`/data/atlas/rootfs.img`) on the real `userdata` partition - the *same*
physical storage Android's own data lives on, not a separate partition -
matching the project's "one shared system" philosophy even without
Btrfs subvolumes to formalize it.

**Built for real, not just described**:
- Converted the Arch Linux ARM chroot (`libhybris/src/atlas-base/rootfs/`)
  into a real ext4 disk image via `rsync` (had to exclude `/proc`,
  `/sys`, `/dev` from the copy - the live bind-mounts include
  `/proc/kcore`, a virtual "file" that reports as enormous and instantly
  fills any real disk image if copied literally - hit this for real,
  fixed by excluding the live mount paths, not just the excludes I'd
  already planned for `/build`/`/home/builduser`).
- Wrote a real custom `init` script (`libhybris/src/rp6-boot-image/ramdisk/init`)
  using the same static aarch64 `busybox` already used elsewhere this
  session: mounts `/proc`/`/sys`/`/dev`, uses `mdev` to populate device
  nodes, waits for `/dev/block/by-name/userdata` (confirmed this is the
  real partition label via the stock firmware's own `rawprogram.xml`,
  not guessed), mounts it, loop-mounts `/data/atlas/rootfs.img`,
  move-mounts `/dev`/`/proc`/`/sys` into the new root, and
  `switch_root`s into `/sbin/init` - confirmed this resolves to the real
  `systemd` binary in the built Arch rootfs before relying on it.
  Written to drop to an interactive busybox shell (not panic-loop) on
  any failure, with `atlas-init:`-prefixed progress messages to
  `/dev/kmsg`, specifically so a failed real-hardware boot is debuggable
  rather than a silent black box.
- Packed the ramdisk (cpio + gzip) into a new `init_boot.img` via the
  same `mkbootimg.py` already verified this session - **round-trip
  verified**: unpacked the freshly-built image again, `cmp` confirms the
  ramdisk bytes are byte-identical to what was packed, same header
  version (4) and `kernel_size: 0` convention as the real stock
  `init_boot.img`.

**Delivered to `/media/psf/Unreal/CRgOS_boot_test_20260724/`** (per the
user's explicit "you can use this as memory/storage" - see the
`shared_folder_persistence` memory): `init_boot.img`, `rootfs.img`, and a
`README.md` with exact flashing instructions, what's genuinely
unverified, and how to get debug output if it fails.

**Explicitly not claimed as working** - what's real and verified: the
packing/round-trip mechanics, the init script's own logic (checked
carefully, not run). What's NOT verified and can't be from here: whether
this actually boots on real RP6 hardware (AVB verification behavior,
`mdev`/uevent timing for `userdata` to appear, whether the kernel accepts
this exact ramdisk format from this exact bootloader chain). First real
signal comes only from an actual hardware test.

## Root cause found and fixed for real: LZ4 vs gzip ramdisk compression mismatch

User connected the physical RP6 to this session directly via Parallels USB
passthrough (`adb`/`fastboot` both work live against the real device,
`product:kalama model:Retroid_Pocket_6`). This unblocked real interactive
hardware debugging instead of relying on the user relaying results by hand.

Flashed `init_boot_v2_diag.img` for real and polled `adb`/`fastboot
devices` continuously for 90-150+ seconds after reboot: **zero response
on either interface**, and the user confirmed visually the logo stayed
perfectly static (no flicker/reboot). Since the v2 diagnostic's watchdog
reboot is the very first line of the script (fires unconditionally at
~20-23s regardless of anything else), this much silence meant `/init`
almost certainly never executed at all - ruled out a script-logic bug,
pointed at the kernel/ramdisk-loading layer itself.

Checked `fastboot getvar all`: `secure:no`, `unlocked:yes` - Secure Boot
is off entirely on this unit, so AVB/verified-boot rejection (the next
obvious hypothesis) doesn't apply. Compared parsed headers
(`unpack_bootimg.py`) between the working stock `init_boot.img` and our
built image - structurally identical (header_version 4, kernel_size 0,
same os_version/patch level encoding). Verified the ramdisk's own cpio
contents (`cpio -tv` on the actual `.gz` that got packed) - `/init`
present, executable, correct shebang, `/bin/busybox` present and
executable alongside it. All of this checked out clean.

**Found the actual bug by unpacking `vendor_boot.img` directly**: its
vendor ramdisk fragment (`vendor_ramdisk00`, the part that gets
concatenated with `init_boot.img`'s ramdisk by the bootloader before
being handed to the kernel as one combined initrd) is **LZ4-compressed**
(`file` confirms: "LZ4 compressed data (v0.1-v0.9)", the legacy/kernel
frame format), not gzip. Our custom `init_boot.img` ramdisk was
gzip-compressed. **A combined initrd blob can't mix compression
algorithms** - the kernel's decompressor detects the format once from
the leading magic bytes and decompresses the *entire* concatenated blob
with that one algorithm; concatenating an LZ4 stream with a gzip stream
produces something neither decompressor can read past the first
fragment, which is consistent with a total, silent, permanent freeze
(no panic text visible because nothing ever gets far enough to touch the
framebuffer).

**Fix confirmed empirically, not just theorized**: rebuilt a minimal
test ramdisk (mount `/dev`, log to kmsg, sleep 10s, `reboot -f`) with
`lz4 -l` (legacy/kernel-compatible frame format, matching
`vendor_ramdisk00` exactly) instead of gzip. Flashed it - **the device's
logo started blinking/rebooting on a ~10s cycle**, exactly matching the
script's own sleep timer. This is direct, positive proof `/init` now
executes. Confirmed by reverting to stock and back multiple times during
the session without incident - the device is fully recoverable at every
step (`fastboot flash init_boot init_boot_stock.img` restores normal
boot every time, verified repeatedly).

## New real blocker found: `userdata` is FBE-encrypted (F2FS, inlinecrypt)

Once `adb` access was available (device booted normally, USB debugging
authorized), inspected the live device directly rather than assuming:
`ro.crypto.type=file`, `ro.crypto.state=encrypted`, `/data` is F2FS
mounted with `inlinecrypt` on a device-mapper node (`dm-21`), while
`/dev/block/by-name/userdata` points at the *raw* partition (`sda17`)
underneath. This is File-Based Encryption (fscrypt), not classic
whole-disk dm-crypt - meaning the raw partition's filesystem structure
is visible without a key, but individual files/directories under a
fscrypt encryption policy (likely including `/data/media/0`, i.e.
`/sdcard`) need the same hardware-backed key Android's own
vold/keystore/TEE stack derives at boot - something a bare custom
initramfs `/init` has no way to replicate. This directly threatens the
storage-architecture plan ("plain rootfs.img file living on the shared
`userdata` partition, mounted by a first-stage custom init") - the file
might be unreadable/garbage if the custom init tries to read it before
Android's own userspace has unlocked FBE.

Checked for a repartitioning option (a genuinely separate, unencrypted
partition for CR(g), carved out of `userdata`): confirmed via
`/sys/block/sda/sda17/{start,size}` that `userdata` already extends to
within ~2MiB of the end of the physical disk (`sda`, ~972GB) - **no free
unpartitioned space exists**, so a new partition would require shrinking
the live, currently-mounted, FBE-encrypted `userdata` filesystem, a
materially riskier operation than using free space. Checked for a
physical microSD slot as a zero-risk alternative - none currently
inserted (`/storage/` shows only `emulated`, no `mmcblk*` device nodes
at all).

User pointed out armada's own installer already solves exactly this
class of problem for its own supported devices - checked
`system_files/usr/libexec/armada/armada-installer` directly rather than
trusting the claim blind: **confirmed real, tested, safety-checked logic
exists** (`parted`/`sgdisk`/`sfdisk`+`jq` partition discovery by
`PARTLABEL`, shrink-by-delete-and-recreate, safety checks like
refuse-self, unmount-before-destroy, sleep-inhibit, recovery
instructions on failure). Important caveat found: **it is not F2FS/FBE
aware at all** - it only manipulates the GPT partition-table entry and
zeroes the new partition's first 8MiB, relying on Android's own next
boot to notice a missing/corrupt filesystem and reformat `userdata`
itself. Reusable as a proven GPT-surgery pattern, not as a
filesystem-preserving resize - noted for future work, not applied yet.

**Decided (2026-07-24, live with user): defer repartitioning entirely
for now.** Pragmatic path chosen for testing: let Android boot
completely normally (which unlocks FBE naturally via its own boot
flow), push `rootfs.img` to `/sdcard/rootfs.img` (writable by the
unprivileged `shell` adb user, no root needed - and physically the same
`userdata` partition, "one shared disk" still holds even without a
dedicated CR(g) partition), then pivot into it via a **late handoff**
(mount/chroot *after* Android's own userspace is already up), instead
of a first-stage-init `switch_root` replacing Android's boot chain
entirely. Explicitly logged as a simplification for testing, not a
final architecture decision - "потом переделаем" (revisit properly
later, once the basic mechanics are proven to work at all).
